## 확인된 구조

### 문자 선택 그리드 — `0x08ADEC`, `0x08B142`

이름 입력 화면에서 쓰는 문자표입니다. **셀당 2바이트 고정폭**, 행당 16셀입니다.

- 반각 문자: `20 XX` — 상위 바이트가 `0x20`, 하위 바이트가 ASCII 코드
- 전각 문자: Shift-JIS 2바이트를 그대로 저장
- 빈칸: `20 20`

| 오프셋 | 셀 수 | 내용 |
| --- | --- | --- |
| `0x08ADEC` | 384 | 반각 ASCII 전체 → 전각 숫자 → 전각 영대문자 → 히라가나 |
| `0x08B142` | 597 | 가타카나(탁음·반탁음·요음 포함) → 상용 한자 약 215자 |

중복을 제거하면 **522자**입니다. 추출:

```bash
make grid          # build/grid_*.tbl 생성 (ROM 파생물이라 커밋하지 않습니다)
make grid-find     # 다른 그리드 후보 탐색
```

시사점: 게임이 **Shift-JIS를 그대로 다루는 경로가 존재**합니다. 다만 이 표는
이름 입력용이며, 본편 스크립트가 같은 인코딩을 쓴다는 근거는 아직 없습니다.

### 압축 데이터 — GBA 표준 LZ77

ROM 전역에서 GBA BIOS 표준 LZ77(`0x10`) 블록이 쓰입니다.

포인터 유도 스캔(`--via-pointers`) 결과:

| 항목 | 값 |
| --- | --- |
| 검사한 포인터 대상 | 34,110곳 |
| 유효 압축 블록 | **353개** |
| 압축 해제 후 총량 | **13,057,829바이트** |
| 평균 압축률 | 약 45–60% |

ROM 16MB 중 13MB가 압축 데이터이므로, 대부분이 그래픽·사운드로 보입니다.

> 전수 스캔(4바이트 정렬 400만 곳)은 수십 분이 걸립니다. 압축 블록은 거의 항상
> 포인터로 참조되므로 `--via-pointers` 를 쓰면 수 분으로 줄어듭니다.

```bash
make scan-lz       # 또는: python3 tools/gbalz.py scan ROM --via-pointers
```

## 미확인 / 진행 중

### 본편 스크립트 — 위치·압축·인코딩 확인 완료

정적 디스어셈블(`tools/disasm.py`)로 호출 경로를 역추적해 전부 밝혀냈습니다.

#### 호출 경로

```
VM 핸들러 0x08039CCC(ctx, ?, id, kind)
  └ kind != 2 면 즉시 0 반환
  └ 0x08038930(id)
      └ table = *(u32*)(0x02002C00 + 0xAC)     ; EWRAM 전역에 담긴 테이블 포인터
      └ 0x0800D574(table, id)                  ; 테이블 조회
          └ 0x0800D558(addr)                   ; 4KB 작업 버퍼로 전개
              └ 0x0800D4F8(addr, 0x1000)       ; 압축 해제 본체
          └ 반환 0x02002E60 (EWRAM 작업 버퍼)
  └ 0x0801B8C8(ctx, 버퍼)                      ; 출력
```

#### 문자열 테이블 형식 (`0x0800D574`)

```
table[0]          엔트리 개수
table[id]         테이블 기준 상대 오프셋
주소 = table + table[id]
유효 범위는 0 < id < count. 벗어나면 빈 문자열 0x08089D44 를 반환합니다.
```

#### 압축 형식 (`0x0800D4F8`)

출력 바이트 수를 예산으로 삼는 LZ 계열입니다. **역참조가 압축 스트림 자체를
가리키며 재귀적으로 전개**되는 점이 특징입니다.

| 바이트 | 의미 |
| --- | --- |
| `0x08` | 이스케이프. 뒤 2바이트 `b1 b2` — 길이 `(b1>>4)+4`, 거리 `((b1&0x0F)<<8)\|b2` |
| `0x00` | 종결자 |
| 그 외 | 문자 코드 그대로 |

**거리 0 은 오류가 아닙니다.** 루틴은 `src = r4 - dist` 를 그대로 쓰므로
(`0x0800D526`), 거리 0 이면 이스케이프 **바로 다음 위치**부터 길이만큼 한 번 더
전개한 뒤, 같은 자리에서 정상 전개를 이어갑니다. 결과적으로 뒤이어 나올 출력
`length` 바이트가 두 번 나옵니다. 이 동작을 반영해 **전개 실패 162건이 0건**이
되었습니다 (`tests/test_obtext.py`).

#### 문자 인코딩

전개된 텍스트는 `<코드> <파라미터>` 형태가 주를 이룹니다. 디코더 `0x0803894C`
가 코드 `1`–`5` 에 대해 뒤따르는 1바이트를 함께 읽습니다.

**뱅크 계산은 완전히 일반적입니다.** 본문 렌더 루프 `0x0801C7D8`:

```
0801C7D8  ldrb r4, [r6]        ; 토큰 바이트
0801C7DC  subs r0, r4, #1
0801C7E2  cmp  r0, #4
0801C7E4  bhi  0x801C7EE       ; 1..5 가 아니면 그대로 문자 코드
0801C7E6  lsls r4, r4, #8      ; code = byte << 8
0801C7EA  orrs r4, r0          ; code |= param
0801C7EE  cmp  r4, #0x7f       ; <=0x7F 작은 폰트, >0x7F 큰 폰트
```

즉 `01`–`05` 가 모두 같은 식으로 처리되므로 **문자 코드 공간은 `0x000`–`0x5FF`
(1,536칸)** 입니다. 그리드가 채우는 것은 그중 앞의 `0x300` 칸뿐입니다.

| 코드 | 텍스트 테이블 출현 | 해석 |
| --- | --- | --- |
| 직접(≥6) | 284,624 | 1바이트 문자 (`0x000`–`0x0FF`) |
| `01` | 79,886 | 뱅크 1 (`0x100`–`0x1FF`) |
| `02` | 16,538 | 뱅크 2 (`0x200`–`0x2FF`) |
| `03` `04` `05` | **0** | **뱅크 3·4·5 — 통째로 비어 있음** |

> 이전 기록의 `03`(250) `04`(429) `05`(292)는 오류였습니다. 텍스트가 아닌
> **크기 접두 바이너리 블롭 테이블 16개를 함께 센 값**입니다. 텍스트 테이블만
> 세면 세 코드 모두 **정확히 0회**입니다.

**한글화에 그대로 쓸 수 있는 여유 공간 768칸**이 이미 배선까지 끝난 채로
비어 있다는 뜻입니다. 폰트 배열을 `0x600` 엔트리로 늘리고 EWRAM 베이스
포인터만 옮기면 됩니다 (두 폰트 배열 뒤는 현재 전부 `00`).

#### 단일 바이트 제어 코드 (0x21 미만)

양쪽 폰트 모두 `0x00`–`0x1F` 에 글리프가 없습니다. 순수 제어 코드입니다.
아래는 **문맥 기반 가설**로, 아직 코드로 확인하지 않았습니다.

| 코드 | 횟수 | 위치 | 문맥 | 가설 |
| --- | --- | --- | --- | --- |
| `0x10` | 3,440 | 처음 3,439 | `<10>\n…` | 메시지 시작 |
| `0x12` | 917 | 혼합 | 단독 문자열 다수 | 빈 메시지 · 자리표시 |
| `0x14` | 463 | 중간 437 | `<14>の こうげき` | **이름 삽입** |
| `0x19` | 303 | 항상 `<10>` 직후 | `<10><19>004\n` | 번호·식별자 |
| `0x15` | 236 | **항상 끝** | `…みますか<01:26>\n<15>` | 예/아니오 선택지 |
| `0x1F` | 191 | 처음 93 | `<1F>sで よろし` | **printf 서식** (확정) |
| `0x13` | 86 | 중간 | `こうげきが\n<13>あがった` | 강조(색) |
| `0x17` | 62 | 중간 | 시구 사이 `\n<17>\n` | 연 구분 |
| `0x16` | 56 | 중간 | 시구 사이 `\n<16>\n` | 연 구분 |
| `0x1A` | 28 | **항상 끝** | `…しますか<01:26>\n<1A>` | 선택지 (0x15 변형) |

`0x1F` 은 **printf 서식 이스케이프**입니다. 뒤따르는 ASCII 문자가 곧 서식
지정자입니다 — `<$1F>s` = `%s`, `<$1F>-3d` = `%-3d`, `<$1F>-02d` = `%-02d`,
`<$1F>c` = `%c`. UI 테이블(`0xDF3908`)에 `<$1F>-3d：<$1F>-02d`(시각),
`ＨＰ<$1F>-3d／<$1F>-3d` 같은 조합이 그대로 들어 있어 의심의 여지가 없습니다.
**번역할 때 서식 문자까지 그대로 보존해야 합니다.**

`0x0A` 는 개행, `0x00` 은 종결자로 확인되었습니다.
`0x20` 은 **공백**입니다 — 그리드에서는 빈칸이지만 본문에서 865회 쓰이고,
작은 폰트의 글리프가 8바이트 전부 `00` 입니다.

### 문자열 테이블 오탐 — 크기 접두 바이너리 블롭 (확정)

`obtext.py scan` 의 테이블 시그니처는 **텍스트가 아닌 데이터 테이블도 통과**합니다.
후보 133개 중 16개가 이에 해당하며, 판별 규칙이 아주 깨끗합니다.

```
엔트리 선두 u32 + 4 == 다음 엔트리까지의 간격
```

즉 각 엔트리는 `[u32 길이][데이터…]` 형태의 블롭입니다. 이 규칙의 일치율은
**16개 테이블에서 정확히 100%, 나머지 117개에서 2% 미만**이라 임계값에
민감하지 않습니다.

| 블롭 테이블 | | |
| --- | --- | --- |
| `0x220020`(600) | `0x26CAC8`(1,383) | `0xCAE740`(116) |
| `0xD7DE5C`(84) | `0xDAAA70`(59) | `0xDAAB68`(256) |
| `0xE02DA4`(227) | `0xE3DC5C`(53) | `0xE5A3D0`(103) |
| `0xE7E6E0`(113) | `0xE9D308`(127) | `0xEBEB48`(153) |
| `0xEE8E58`(57) | `0xEF54D0`(107) | `0xF0C118`(101) |
| `0xF2E98C`(219) | | 합계 **3,758항목** |

확인 예 — `0xCAE740` #1 은 선두가 `0x1674`(5,748)이고 다음 엔트리까지 간격이
`0x1678`(5,752)입니다. 전개하면 `74 16 00` 세 바이트에서 바로 종결자를 만나므로
"길이 3의 문자열"처럼 보였던 것입니다.

`tools/dumpscript.py` 가 이 테이블들을 건너뜁니다. 덕분에 번역 대상이
20,166개에서 **16,676개**로 줄었습니다.

### 영문 패치 ROM 대조

이 게임은 해외 정식 발매가 없었으므로, 흔히 "북미판"으로 도는 파일은
**영문 팬 번역 패치가 적용된 ROM**입니다.

| 항목 | 일본판 | 영문 패치판 |
| --- | --- | --- |
| 크기 | 16,777,216 | 16,777,216 (동일) |
| 내부 타이틀 / 코드 | `ORIENTALBLUE` / `AORJ` | 동일 |
| CRC32 | `05E80ECC` | `8A850DA7` |
| SHA-1 | `414cad1a…` | `95c4e8b7…` |

대조 결과:

| 측정 | 값 | 해석 |
| --- | --- | --- |
| 전체 상이 바이트 | 11,281,332 (67.24%) | 데이터 영역을 대폭 재구성 |
| **앞 1MB(코드 영역) 상이** | **2,961바이트 (0.28%)** | 엔진 훅은 소규모 |
| 128B 이상 동일 구간 | 392개 / 4,389,063B | 최장 `0x26E06B`(1.8MB), `0x0BD23A`(1.0MB) |
| 영문판 평문 ASCII 비율 | 1.24% | **영문판도 평문으로 저장하지 않음** |

가장 중요한 결과는 마지막 줄입니다. 영문 패치판조차 텍스트가 평문 ASCII로
보이지 않으므로, **게임 고유의 인코딩/압축 체계를 그대로 유지한 채 번역**한
것입니다. 즉 우리도 같은 체계를 해독해야 합니다.

### 이벤트 VM 레코드 — `0x092000`–`0x0A4000` (구조 확정)

영문 패치가 집중적으로 수정한 구간입니다. **20바이트 고정 레코드**가
연속으로 늘어서 있습니다 (레코드 2,234개, 핸들러 438종).

```
+0   u16  field0     인덱스/순번으로 추정
+2   u16  width      메시지 창 줄당 글자 수
+4   u16  lines      메시지 창 줄 수
+6   u32  handler    THUMB 함수 포인터 (최하위 비트 = 1)
+10  u16  field10    순번 (0,1,2,… 로 증가하는 사례 다수)
+12  u16  field12
+14  u16  field14
+16  u16  field16
+18  u16  field18
```

레코드 크기는 포인터 간 간격 분포에서 확정했습니다 — 20바이트가 2,194회로 압도적.

#### width / lines 의 의미 (확인됨)

핸들러 `0x0803B604` 의 레코드 16개는 **전부 일관**됩니다.

| 필드 | 일본판 | 영문 패치판 |
| --- | --- | --- |
| `width` | 8 (16/16개) | 16 (16/16개) |
| `lines` | 2 (16/16개) | 1 (16/16개) |
| `field12` `field14` `field16` | 동일 | 동일 |

같은 `8×2 → 16×1` 변화가 `0x08045304`, `0x08046EC8`, `0x080472A4`,
`0x08046F00`, `0x08047018` 에서도 각각 16회씩 나타납니다.

**일본어 전각 8자 × 2줄 = 영어 반각 16자 × 1줄** — 전각 1칸이 반각 2칸이므로
픽셀 폭이 보존됩니다. 즉 이 필드의 단위는 픽셀이 아니라 **문자 칸**입니다.

> **한글화 시사점**: 한글을 전각 폭(일본어와 동일)으로 렌더링하면 일본판 값
> `8×2` 를 **그대로 두면 됩니다**. 반각에 가까운 좁은 한글 폰트를 쓸 경우에만
> 이 필드를 다시 계산해야 합니다. 폰트 폭 결정이 이 값에 직결됩니다.

```bash
python3 tools/vmrec.py rom/baserom.gba --stats --min-count 8
python3 tools/vmrec.py rom/baserom.gba --fn 0x0803B604 --diff 영문판.gba
```

#### 주의 — 필드 의미는 핸들러마다 다릅니다

처음에는 레코드 2,234개를 한꺼번에 통계 냈고, 그 결과 `(2,8) → (1,16)` 처럼
필드 순서가 뒤바뀐 듯한 사례와 곱이 보존되지 않는 273건이 섞여 나왔습니다.
**핸들러 438종을 구분하지 않은 탓**이었습니다. 같은 20바이트 틀을 쓰더라도
인자의 의미는 핸들러마다 다르므로, 반드시 `--fn` 으로 나눠서 봐야 합니다.

| --- | --- |

| `0x08039CF4` | 179 |

1순위입니다.

### 문자 대응표 — 확정

문자표는 이름 입력 그리드와 **같은 배열**입니다. `0x08ADEC` 부터 셀당 2바이트가
연속으로 이어지며, **문자 코드가 곧 셀 인덱스**입니다.

```
코드 = (뱅크 << 8) | 인덱스

  0x000–0x0FF   본문에 1바이트로 그대로 등장
  0x100–0x1FF   `01 XX` 2바이트로 등장
  0x200–0x2FF   `02 XX` 2바이트로 등장
```

#### 확정 근거

1. **빈도 일치** — 직접 코드의 최빈값들이 일본어 히라가나 빈도와 정확히 맞습니다.
   `0xC3`=の(13,645회), `0xAC`=い, `0xB0`=か, `0xAD`=う, `0xB6`=し, `0xBA`=た,
   `0xD8`=ん, `0xBF`=な, `0xBE`=と, `0xC4`=は … 상위 14개가 전부 고빈도 히라가나입니다.
2. **셀 인덱스 일치** — `'あ'` 는 그리드 셀 171번이고 코드도 `0xAB`(=171)입니다.
   최빈 코드 `0x90`(26,886회)은 셀 144번 전각 공백으로, 최다 출현이 자연스럽습니다.
   ASCII 구간도 `코드 == ASCII 값` 으로 그대로 맞아떨어집니다.
3. **실문자열 검증** — 이 대응표로 디코딩하면 몬스터·인물 이름이 정상적인
   일본어로 읽힙니다. 뱅크 기준점을 `0x180`/`0x280` 으로 바꾸면 의미 없는
   한자 나열이 되어, 기준점이 `0x100`/`0x200` 임이 확정됩니다.

#### 대응 범위

| 구분 | 자수 |
| --- | --- |
| 직접 (1바이트) | 211자 |
| 뱅크 `01` | 151자 |
| 뱅크 `02` | 198자 |
| **합계** | **560자** |

실제 텍스트에 쓰인 코드 600종 / 381,717회 중:

| 분류 | 종수 | 횟수 | 비율 |
| --- | --- | --- | --- |
| 대응 성공 | 535 | 373,180 | 97.76% |
| `0x21` 미만 (제어 코드 영역) | 25 | 7,732 | 2.03% |
| 뱅크 인덱스 0 | 2 | 658 | 0.17% |
| **실질 미해결** | **38** | **147** | **0.04%** |

`0x21` 미만 코드는 그리드 앞 32칸이 비어 있는 자리라 문자가 아니라 제어 코드입니다
(`0x10` 이 3,509회로 최다). 실질 미해결 38종은 출현이 1–56회로 희소합니다.

```bash
make tbl          # build/ja.tbl 생성
make tbl-check    # 실사용 코드 대응률 확인
```

> 생성물은 ROM 파생물이므로 `build/` 에만 두고 커밋하지 않습니다.
> 한글 테이블은 이 코드 공간에 맞춰 만들되, 폰트 글리프를 교체할 때
> 셀 인덱스 순서를 그대로 유지해야 합니다.

### 폰트와 글자 출력 경로 (확정)

정적 탐색 5종이 모두 실패한 뒤 **mGBA GDB 스텁으로 동적 분석**해 전부 밝혔습니다.

#### 폰트 세 벌

| 이름 | 위치 | 크기 | 형식 | 색인 | 글리프 |
| --- | --- | --- | --- | --- | --- |
| **작은** | `0x0D7DFB8` | 8×8 | 1bpp / 8바이트 | **문자 코드** | 586자 |
| **큰** | `0x0D7FFBC` | 8×16 | 1bpp / 16바이트 | **문자 코드** | 494자 |
| 시스템 | `0x00BD7E0` | 8×8 | 4bpp / 32바이트 | JIS X 0201 | 224자 |

본문에 쓰이는 것은 앞의 두 벌입니다. 행당 1바이트, MSB가 왼쪽 픽셀이며 **비압축
평문**입니다. 작은 폰트 586자는 문자 대응표 자수와 정확히 일치합니다.

**반각/전각이 아니라 같은 문자 집합의 크기 두 종류입니다.** 490자가 양쪽에 다
들어 있고(`あ` 는 두 벌 모두 `0xAB`), **둘 다 8픽셀 폭**입니다. 차이는 높이뿐
입니다. 렌더러는 코드가 `0x7F` 이하면 작은 폰트, 초과면 큰 폰트를 씁니다.

큰 폰트의 `0x21`–`0x7E` 는 **전부 비어 있습니다**(94자). ASCII는 작은 폰트가
그리기 때문입니다. 정적 스캔이 실패한 이유가 바로 이것으로, 탐색기가 "ASCII
구간에 글리프가 있을 것"을 전제했습니다.

시스템 폰트는 본문 경로와 무관합니다. `0x08074F58` 이 팔레트 `0x00BD7C0`(16색
BGR555)와 함께 VRAM `0x0600E000` 으로 통째 복사합니다.

#### 출력 경로

```
초기화 0x0801C264
  아카이브 0x08220000 조회(0x08000324, 인덱스 3) -> 폰트 묶음
    0x02001A48 = 반각 베이스  -> 0x08D7DFB8
    0x02001A4C = 전각 베이스  -> 0x08D7FFBC
  니블 확장 LUT 0x0808F190 (32바이트) -> 0x02001AE8

글리프 인출
  0x0801C2D0  get_half(dst, code)   memcpy(dst, [0x02001A48] + code*8,  8)
  0x0801C2EC  get_wide(dst, code)   memcpy(dst, [0x02001A4C] + code*16, 16)

1bpp -> 4bpp 확장
  0x0801C308  expand(dst, ink, bg, src, rows)
    글리프 1바이트 = 8픽셀. 니블 단위로 LUT를 찾아 16비트 마스크를 얻고
    out = (ink & mask) | (bg & ~mask) 를 2바이트씩 기록한다.
```

LUT 16개(u16): `0000 F000 0F00 FF00 00F0 F0F0 0FF0 FFF0 000F F00F 0F0F FF0F
00FF F0FF 0FFF FFFF` — 니블의 MSB가 왼쪽 픽셀임을 확인해 줍니다.

#### 찾은 방법

1. mGBA AppImage 를 `-g` 로 띄워 GDB 스텁(포트 2345) 개방 — sudo 불필요
2. 파이썬으로 GDB 원격 시리얼 프로토콜을 직접 구현 (`gdb-multiarch` 불필요)
3. XTEST 로 키를 넣어 대사창까지 진행하고 세이브스테이트로 고정
4. VRAM 96KB 덤프 → 타일 렌더 → `0x1EA0` 에서 `さ` 발견 (잉크 = 팔레트 15)
5. 8×8 마스크 `7F 04 04 3E 42 40 3C 00` 을 ROM 전체에서 검색 → `0xD80B14` 적중
6. `さ` 는 코드 `0xB5` 이므로 base = `0xD80B14 - 0xB5×16` = `0xD7FFBC`
7. `0x08D80B14` 에 **읽기 워치포인트**(`Z3`) → `pc=0x08083F48`(memcpy),
   `lr=0x0801C2FF` 로 호출자 특정. `r2=0x10`, `r3=0x08D80B18` 이 글리프 16바이트
   복사임을 그대로 보여 줍니다.

```bash
make font-orig     # 검증 + build/font_{wide,small,system}.png
```

#### 그리드에 없는데 폰트에는 있는 문자

| 코드 | 내용 |
| --- | --- |
| `0x151`–`0x16A` | **전각 소문자 ａ–ｚ** — 그리드는 대문자만 제공 |
| `0x2E6` | `宿` — 그리드 밖 한자, 본문 4회 |
| `0x20` | **공백** — 본문 865회, 글리프가 전부 `00` |
| `0x150`, `0x190` | `あ` 중복 글리프 (본문 미사용) |
| `0x120`, `0x122` | 전각 공백 · `，` — 글리프가 비어 있음 |

이들을 `tools/mktbl.py` 의 `SUPPLEMENT` 로 보충해 대응표가 560자 → **588자**가
되었습니다. 그 결과 스크립트에 남은 미해결 태그 5,783회 중 **문자 코드는 단
1회**(`0x142`, 바닥 가로줄 모양, 용도 불명)이고 나머지는 전부 제어 코드입니다.

#### 한글화 시사점

교체 자체는 쉽습니다. 폰트가 비압축이고 색인이 단순하며, **베이스가 EWRAM
변수**라 ROM 빈 공간으로 옮기고 포인터만 바꾸면 크기 제한이 없습니다.

제약은 폰트가 아니라 **문자 코드 공간**입니다.

코드 공간은 `0x000`–`0x5FF`(**1,536칸**)이고, 그중 뱅크 3·4·5(768칸)가 통째로
비어 있습니다. 모든 글자가 8픽셀 폭이라 한글은 두 칸(16픽셀)을 써야 합니다.

| 방식 | 음절당 칸 | 최대 음절 | ASM 패치 |
| --- | --- | --- | --- |
| 8×16 한 칸 | 1 | 약 1,400 | 불필요 (폰트 확장만) |
| 16×16 두 칸 | 2 | 약 700 | 불필요 (폰트 확장만) |
| 조합형 합성 | 2 | 제한 없음 | 필요 |

#### 실측 — 완성형은 한도를 넘습니다 (확인됨)

UI·마석·지명·몬스터 테이블 **1,848항목(전체의 11.1%)**을 번역한 시점의 수치입니다.

| 항목 | 값 |
| --- | --- |
| 한글 코드 풀 | 1,398개 → **699자** (절대 상한) |
| 미번역 원문이 예약 중 | 464개 |
| 지금 쓸 수 있는 음절 | **467자** |
| 실제로 필요한 음절 | **540자** |
| 부족 | **73자** |

번역이 진행되면 예약이 풀려 한도가 699까지 올라가지만, 필요량이 더 빠르게
늘어납니다. 관측값으로 Heaps 법칙(V = K·N^β)을 맞추면 β≈0.44 이고,
전체 16,674항목에서는 **900–1,400자**가 필요합니다.

| 번역 항목 | 고유 음절 |
| --- | --- |
| 246 | 221 |
| 474 | 335 |
| 865 | 431 |
| 1,848 | **540** |

즉 **완성형만으로는 전체 번역을 끝낼 수 없습니다.** 11% 지점에서 이미 상한의
77%를 썼습니다. 고유명사(인명·지명·몬스터명)가 음절을 빠르게 소모합니다.

**조합형 전환이 필요합니다.** 번역문 자체는 `script/ko/` 에 그대로 남으므로
버려지지 않고, 전환 후 그대로 다시 삽입됩니다.

훅 지점은 명확합니다.

- `get_wide(dst, code)` 는 명령 8개짜리 단순 memcpy 이고 출력이 16바이트
  (8×16 1bpp) 입니다. 초성·중성·종성 비트맵을 OR 로 합치기에 알맞습니다.
- 다만 음절 하나를 16×16 으로 그리려면 **코드 두 개를 함께 봐야** 합니다.
  훅은 `get_wide` 보다 렌더 루프 `0x0801C7D8` 쪽이 맞습니다 — 여기서 한글
  선행 코드를 만나면 다음 코드까지 읽어 16×16 을 합성하고 두 칸을 채우면
  됩니다. 코드 쌍이면 조합을 표현하기에 공간이 넉넉합니다
  (예: 선행 = 초성+중성 399가지, 후행 = 종성 28가지).
- `expand()` 는 색상까지 처리하므로 손댈 필요가 없습니다.

### 뱅크 3 실물 검증 (완료)

한글이 **ASM 패치 없이** 화면에 나오는 것을 실제로 확인했습니다.

#### 바꾼 것

| 대상 | 내용 |
| --- | --- |
| 글리프 | `0xD82FCC`–`0xD82FFC` 에 16바이트 글리프 4개 (코드 `0x301`–`0x304`) |
| 문자열 | `0xDF5475` 10바이트를 `03 01 03 02 03 03 03 04 00 00` 으로 교체 |

메뉴 설명문 "さいしょから　はじめます"(테이블 `0xDF3908` #506)가 화면에서
**"한글"** 로 바뀌어 나왔습니다. 두 칸(8×16 × 2)이 이어져 16×16 음절이 빈틈
없이 그려집니다. 글리프는 Galmuri14 를 14px 로 렌더해 왼쪽/오른쪽 절반으로
자른 것입니다.

**포인터 변경도, 폰트 재배치도, 코드 패치도 없었습니다.** 뱅크 계산이 일반적
이라는 분석이 실물로 확인된 셈입니다.

#### 뱅크 3은 기존 여유 공간에 그대로 들어갑니다

| 폰트 | 배열 끝 | 뒤따르는 `00` | 들어가는 뱅크 |
| --- | --- | --- | --- |
| 큰 (16바이트) | `0x0D82FBC` | 4,096바이트 | **뱅크 3 정확히 한 개** (256×16) |
| 작은 (8바이트) | `0x0D7F7B8` | 2,049바이트 | 뱅크 3 (256×8) + 여유 |

코드 `0x300` 이상은 `0x7F` 초과라 **항상 큰 폰트**만 봅니다. 작은 폰트는
건드릴 필요가 없습니다.

뱅크 4·5 까지 쓰려면 큰 폰트 배열이 `0x600`×16 = 24,576바이트 필요한데
제자리에는 16,384바이트(뱅크 0–3)까지만 들어갑니다. 그 이상은 폰트를 ROM 빈
공간으로 옮기고 EWRAM 베이스(`0x02001A4C`)를 채우는 초기화 경로
(`0x0801C264`, 아카이브 `0x08220000`)를 손봐야 합니다.

#### 파라미터 바이트 제약 (중요)

전개기 `0x0800D4F8` 는 스트림을 **구조를 모른 채 선형으로** 훑습니다. 따라서
이스케이프 뒤 파라미터 바이트가 아래 값이면 문자열이 깨집니다.

| 값 | 결과 |
| --- | --- |
| `0x00` | 종결자로 해석 — 문자열이 거기서 끊깁니다 |
| `0x08` | 역참조 이스케이프로 해석 — 뒤 2바이트를 먹습니다 |

실제로 일본어 원문의 뱅크 파라미터는 **전부 `0x20` 이상**(최소 `0x20`, 최대
`0xFB`, 217종)이라 이 문제를 아예 피해 갑니다. 한글 코드를 배정할 때도
`0x00` 과 `0x08` 을 반드시 건너뛰어야 합니다.

#### 쓸 수 있는 코드 수

| 구간 | 조건 | 개수 |
| --- | --- | --- |
| 직접 (`0x21`–`0xFF`) | 1바이트. `0x00`–`0x20` 은 제어 코드 | 223 |
| 뱅크 1·2 | 원문 글리프를 덮어씀 | 254 × 2 |
| 뱅크 3 | 여유 공간에 그대로 | 254 |
| 뱅크 4·5 | 폰트 재배치 필요 | 254 × 2 |
| | **합계** | **약 1,493** |

두 칸 음절이면 **약 746음절**입니다. 한국어에서 빈도 상위 700음절이 일반
문장의 95% 안팎을 덮으므로 대사 대부분은 소화되지만, 고유명사에서 막힙니다.

재현 스크립트는 `~/다운로드/hanguel2/mgba/bank3.py` 에 있습니다.

### 조합형 자모 합성 — 기각

완성형이 한도를 넘는 것이 확인된 뒤, 조합형(초성·중성·종성 비트맵을 겹쳐
음절을 만드는 방식)을 검토하고 **기각했습니다.**

출력 경로가 비트맵을 OR 로 합치므로, 자모 비트맵은 그 자모를 쓰는 **모든
음절의 교집합**보다 클 수 없습니다. 크면 없는 획이 생깁니다. 따라서 교집합이
이론상 최대값이고, 정확도는 벌을 얼마나 잘게 나누느냐로만 올릴 수 있습니다.

Galmuri 전 크기(7·9·11·14, 12–16px)로 측정한 결과입니다.

| 벌 나누기 | 글리프 | 완전일치 | 평균 오차 | ROM |
| --- | --- | --- | --- | --- |
| 갈래3×받침 / ㄱㅋ×받침 / 갈래3 | 279 | 0.3% | 23.1px | 8.7KB |
| 중성×받침 / 초성×받침 / 중성 | 2,163 | 14.3% | 7.1px | 67.6KB |
| 중성×받침 / 초성×받침 / 초성×중성 | 12,369 | 100% | 0px | 386.5KB |

16×16 글리프의 잉크가 40픽셀 안팎인데 평균 오차 7픽셀은 눈에 띄게 망가집니다.
세 번째 줄은 100%지만 종성을 초성×중성별로 따로 두는 것이라 사실상 음절을
통째로 저장하는 것과 같습니다 — 조합형이 아닙니다.

원인은 폰트입니다. **Galmuri 는 음절마다 개별 디자인된 완성형 폰트**로,
중성 폭에 따라 초성을 줄입니다 (`가` 의 ㄱ 과 `갸` 의 ㄱ 이 다릅니다).
조합용 자모(U+1100–U+11FF)도 들어 있지 않습니다 (호환 자모만 52–94자).

### 음절 직접 색인 + 출력 훅 (채택)

조합형을 버리고, **음절 글리프를 그대로 저장하고 훅이 찾아 쓰는** 방식으로
갑니다. 픽셀이 원본과 완전히 같고 음절 수 제한이 없습니다.

#### 인코딩

음절 하나가 8픽셀 칸 두 개를 쓰므로 코드도 두 개입니다.

```
앞 코드 = 초성×21 + 중성      399가지
뒤 코드 = 종성                 28가지 (없음 포함)
음절 번호 = 앞×28 + 뒤         11,172가지
```

코드 427개만 쓰면 한글 전체가 표현됩니다 (쓸 수 있는 코드는 1,398개).

#### 자료

| 자료 | 크기 |
| --- | --- |
| 색인 테이블 `SLOT[11172]` (u16) | 22,344바이트 |
| 글리프 `GLYPHS[쓰인 음절][32]` | 음절당 32바이트 |

음절 1,500자 기준 약 70KB. 자유 공간 935KB 중 문자열이 약 400KB 를 쓰므로
넉넉합니다. 쓰지 않는 음절은 슬롯 0 으로 두어 저장하지 않습니다.

#### 훅 (`tools/kohook.py`, 132바이트)

`0x0801C904` 의 `bl get_wide` **대상 주소만 바꿉니다.** 이 자리에서는 스트림
포인터 `r6` 이 살아 있고, `r6` 은 방금 읽은 토큰 **바로 뒤**를 가리킵니다.

```
앞 코드 차례   뒤 코드는 [r6], [r6+1]      아직 안 읽음
뒤 코드 차례   앞 코드는 [r6-4], [r6-3]    이미 읽음
```

그래서 **상태 변수가 필요 없습니다.** 두 칸이 각자 음절 전체를 알아냅니다.
RAM 을 한 바이트도 새로 쓰지 않습니다.

```
hook(r0 = 16바이트 버퍼, r1 = 코드):
    뱅크 5 면   [r6-4],[r6-3] 에서 앞 코드를 읽고 오른쪽 절반
    뱅크 3·4 면 [r6+1] 에서 뒤 파라미터를 엿보고 왼쪽 절반
    그 밖이면   원래 get_wide 로 넘긴다
    음절 번호 = 앞×28 + 뒤, 범위 밖이거나 슬롯 0 이면 빈 칸
    글리프 32바이트에서 두 바이트 간격으로 16행을 옮긴다
```

칸마다 코드 하나라는 루프 구조를 건드리지 않습니다. 바꾸는 기존 코드는
`bl` 하나(4바이트)뿐입니다.

#### 렌더러가 넷이고, JPN 표식으로 갈립니다 (확정)

게임에 **현지화 분기가 남아 있습니다.** `0x080733C2` 가 ROM `0x0FBFFD0` 의
세 바이트를 읽어 `"JPN"` 인지 검사하고, 결과를 `0x0800E980` 으로 EWRAM
`0x020019B0` 에 저장합니다. `0x0800E8F8` 이 그 값을 돌려주고, 곳곳에서
렌더러를 고르는 데 씁니다.

원본에는 `0x0FBFFD0` 에 `"JPN\r\n"` 이 들어 있습니다. 이 바이트들은 `0xFF` 가
아니므로 자유 공간 탐지(`0xFF` 연속 구간)에 절대 걸리지 않습니다 — 삽입기가
덮어쓸 위험이 없습니다.

```
0x0801CD60 디스패처
    flag == 0 (JPN)  -> 0x0801C794   본문 루프, get_wide, 16행
    flag != 0        -> 0x0801CA74   두 번째 루프, get_half, 16행
```

| 렌더 함수 | 글리프 인출 | 스트림 | 칸 높이 | JPN 에서 | 한글 |
| --- | --- | --- | --- | --- | --- |
| `0x0801C794` | `get_wide` (`0x0801C904`) | `r6` | **16행** | 쓰임 | **정상** |
| `0x0801CA74` | `get_half` (`0x0801CBF0`) | `r6` | 16행 | **안 쓰임** | — |
| `0x0801C574` | `get_half` (`0x0801C5E8`) | **`r8`** | **8행** | 쓰임 | 잘림 |
| `0x0801C3F0` | `get_half` (`0x0801C42A`) | ? | **8행** | 쓰임 | 잘림 |

`0x0801CA74` 는 **비-JPN 전용**입니다. 지금 설정(JPN 유지)에서는 돌지 않지만,
표식을 바꿀 경우를 위해 훅은 걸어 두었습니다.

메뉴 렌더러(`0x0801C574`)는 실기에서 **호출 200회 중 190회가 한글 코드**였습니다.
스트림 포인터가 `r6` 이 아니라 `r8` 인 것도 브레이크포인트로 확인했고, 그 자리
문자열은 "아니오" 였습니다.

#### 8행 렌더러용 8×8 글리프 (적용)

8행 렌더러는 `movs r1,#8` 로 행 수를 넘기고 32바이트(8×8 4bpp)씩 옮깁니다.
16×16 한글이 원리적으로 안 들어가므로 **8×8 글리프 표를 따로** 두었습니다.

    슬롯 번호는 16×16 표와 공유합니다 (색인 테이블 하나로 둘 다 찾습니다)
    앞 코드 칸에 음절을 그리고, 뒤 코드 칸은 비웁니다
    Galmuri7 을 8px 로 렌더 — "예아니오 이름 성별 공격 방어" 가 읽힙니다

`0x0801C574`(메뉴)에 적용했습니다. 글자가 한 칸씩 띄어 보이고, 칸을 두 개씩
쓰므로 **긴 문자열은 끝이 잘립니다** — 메뉴에 나가는 문구는 짧게 써야 합니다.

`0x0801C3F0` 은 아직 적용하지 않았습니다. 이 함수는 **문자 하나를 인자로 받고**
(`0x0801C41E` 에서 `cmp r6, #0x51F` 로 코드 범위를 검사) 스트림이 없어서,
짝 코드를 알아낼 방법이 없습니다. 실기에서 한글 코드를 받는 것도 아직
확인되지 않았습니다.

### 동적 분석 환경 (구축 완료)

정적 스캔의 한계는 폰트 탐색에서 드러났고, 동적 분석으로 해결했습니다. 재현에
필요한 것은 mGBA 하나뿐이며 **sudo 도 `gdb-multiarch` 도 필요 없습니다.**

```bash
# mGBA AppImage (설치 불필요)
curl -LO https://github.com/mgba-emu/mgba/releases/download/0.10.5/mGBA-0.10.5-appimage-x64.appimage
chmod +x mGBA-0.10.5-appimage-x64.appimage

# GDB 스텁(포트 2345)을 열고 세이브스테이트에서 재개
./mGBA-0.10.5-appimage-x64.appimage -g -t rom/baserom.ss1 rom/baserom.gba
```

- GDB 원격 시리얼 프로토콜을 파이썬 소켓으로 직접 말하면 됩니다. 필요한 명령은
  `?`(상태) `g`(레지스터) `m`(메모리 읽기) `c`(재개) `Z2/Z3/Z4`(쓰기/읽기/접근
  워치포인트)뿐이고, mGBA 는 셋 다 지원합니다.
- **스텁은 재접속을 받지 않습니다.** 한 세션에서 할 일을 다 끝내거나, mGBA 를
  다시 띄워야 합니다.
- 키 입력은 X11 XTEST 로 창에 직접 넣습니다 (`python-xlib`). 화면 확인은
  `import -window <id>` 로 찍습니다.
- 진행 지점은 세이브스테이트(`rom/baserom.ss1`, Shift+F1)로 고정해 두면 매번
  같은 화면에서 재개할 수 있습니다.

### 끝말잇기 낱말표 — `0xDF9088` / `0xDF9080` / `0xDFBEE4` (번역 보류)

`0xDF9088` 은 항목 세 개가 한 벌인 끝말잇기(しりとり) 낱말표입니다.
525벌 × 3 = 1,575항목.

    [읽기 첫 글자] [낱말] [읽기 마지막 글자]
    い              イガ    が            <- 읽기 "いが" 의 앞뒤 글자
    あ              青のれい水  い        <- 읽기 "あおのれいすい"

앞 220벌 남짓은 일반 낱말(あぶ·いのち·ねこばば…), 나머지는 게임 안
아이템 이름이라 `0xDE1AF8` 과 겹칩니다. 153–517번째에 `ん` 으로 끝나는
낱말 80개가 몰려 있는데, 일본식 끝말잇기에서 지는 낱말들입니다.

`0xDFBEE4` 는 같은 구조의 **비-JPN(영문) 사본**입니다. 1,384항목이지만
고유 문자열은 55개뿐이고 그중 339개가 `dammy`, 나머지는 a–z 표본 낱말
(`apple`·`bee`·`cat`…) 입니다. **개발 중 버려진 자리**이고, JPN 표식 분기
(`0x080733C2`) 때문에 이 ROM 에서는 실행되지 않습니다 — 번역 대상이 아닙니다.

`0xDF9088` 을 한글로 옮기려면 앞뒤 글자도 한글 음절로 바꿔야 사슬이
이어집니다. 다만 **비교 루틴을 아직 찾지 못했습니다.** 한글 음절은 코드
두 개(4바이트)라서, 비교가 한 글자를 1코드로 가정하고 있으면 종성이
빠진 채 맞춰집니다(`강` == `가`). 낱말만 한글로 바꾸고 앞뒤 글자를 가나로
두면 사슬이 화면과 어긋나고, 일부만 옮기면 한·일 낱말이 섞입니다.
그래서 **비교 루틴을 확인할 때까지 이 표는 손대지 않습니다.**

    확인할 것: 앞뒤 글자를 읽어 비교하는 코드의 위치와 비교 길이

`0xDF9080` 은 같은 낱말 자료의 조각 37항목입니다 (`バングル`·`とルク`·`るク`·
`あげは`·`くリーム`·`りーム`·`)ム` …). 낱말과 그 꼬리 음절이 뒤섞여 있어
`0xDF9088` 과 한 몸이므로, 같은 이유로 함께 보류합니다.

### 개발용 이벤트 이름표 — `0xDFFE9C` / `0xE011C8` / `0xE0255C` / `0xDFF16C` (번역 대상 아님)

세 표는 항목이 전부 한 줄이고, 대부분 `E\d{3}` 로 시작하는 **개발용 이벤트
레이블**입니다. 합쳐서 390항목.

    E270 まかいのほしゅう２      E185かぐら         restart ヤマタイ
    E236わかなはかい(なし)      テスト１           金のカギ チェック

디버그 메뉴에서 이벤트로 바로 뛰기 위한 이름으로 보이며, `restart`·`テスト１`·
`金のカギ チェック` 같은 항목이 섞여 있습니다. 정규 플레이에서는 화면에
나오지 않으므로 번역하지 않습니다.

`0xDFF16C` 48항목도 같은 성격입니다 (`E018-E020びわげんじょう`,
`E111ＶＳフウカリン`). 합쳐서 438항목.

### 스태프롤 — `0xDF8494` / `0xDF809C` (원문 유지)

114항목 전부 전각 라틴 문자로 된 제작진 이름과 직함입니다
(`ＯＨＪＩ　ＨＩＲＯＩ`, `ＬＥＡＤ　ＧＡＭＥ　ＤＥＳＩＧＮＥＲ`). 사람 이름이라
옮기지 않고, 직함도 관례대로 원문을 둡니다.

`0xDF809C` 66항목은 같은 스태프롤의 배역 목록입니다 (`CAST`, `SAKURA`).
역시 원문을 둡니다. 합쳐서 180항목.

### 서식 문자열과 이름 입력 그리드 — `0xDF3908` (번역 대상 아님)

883항목 중 481항목은 메뉴 설명문이라 옮겼고, 남은 402항목은 옮길 글이
없습니다. 두 갈래입니다.

**printf 서식과 기호** — `<$1F>-3d／<$1F>-3d`, `ＨＰ　<$1F>-3d`, `ＥＸＰ`,
`ＮＥＸＴ`, `Ｇ`, `ーーーー` 같은 자리표시자·구분선입니다. 폭이 픽셀 단위로
맞춰져 있어 손대면 창이 깨집니다.

**이름 입력 그리드** — 512–826번은 이름 입력 화면의 글자판입니다
(히라가나·가타카나 각 80자, 전각/반각 라틴, 숫자, 기호). 한글 이름 입력을
넣으려면 글자판 배치와 커서 이동 코드를 따로 손봐야 하므로
(`tools/dumpgrid.py` 참조) 이번 범위 밖입니다.

### 자리표시자 — `0xDE1AF8` (번역 대상 아님)

1,018항목 중 279항목이 `0` 한 글자뿐입니다. 아이템 표의 빈칸을 메우는
자리표시자이고 화면에 나오지 않습니다.

### 삽입 공간 — 원문 자리 회수 (확정)

한글은 음절 하나가 코드 두 개라 번역문이 원문보다 훨씬 깁니다. 게다가
`tools/inserttext.py` 는 번역문을 **압축하지 않고** 넣으므로, 진행률 73%
시점에서 0xFF 로 채워진 자유 공간 934,919바이트를 전부 써 버렸습니다.

번역한 항목이 쓰던 원문 문자열 자리는 더는 필요 없지만, 이 형식의 LZ 는
**앞서 나온 바이트를 되참조**(`0x0800D4F8`, 거리 최대 4,095)하므로 그냥
비우면 안 됩니다. 남겨 둔 항목이 그 바이트를 읽고 있을 수 있습니다.

실측 결과 **표 경계를 넘는 되참조는 한 건도 없었습니다** (18,547항목 검사).
그래서 항목 단위로 다음과 같이 계산합니다.

    비울 곳 = (번역한 항목이 읽는 바이트) - (남겨 둔 항목이 읽는 바이트)

`inserttext.read_set()` 이 전개 중 읽은 주소를 모으고,
`inserttext.dead_regions()` 가 위 차집합을 16바이트 이상 구간으로 묶어
자유 공간에 더합니다. 회수량은 진행률 73% 기준 약 266KB입니다.

검증: 미번역 6,307항목을 원본 ROM과 패치 ROM에서 각각 전개해 비교했고
전부 일치했습니다.

### 타이틀 화면 그래픽 — `0x6BC6D4` (확정)

타이틀 로고 타일셋은 LZ77 블록 하나(9,577 -> 14,720바이트, 4bpp 타일 460개)로
`0x6BC6D4` 에 있고, VRAM `0x8400`(타일 번호 `0x20`)에 실립니다. 팔레트는
`0x6C0470` 부터 비압축 BGR555 입니다. 포인터를 따라가는 탐색으로는 못 찾았고,
ROM 전체 LZ77 스캔으로 찾았습니다.

**타일맵은 ROM 에 없습니다.** 평문에도 LZ 블록에도 없고(16비트·8비트 두 형식
모두 전수 검색) 런타임에 만들어집니다. 그래서 타이틀에서 뜬 mGBA
세이브스테이트의 VRAM 을 읽어 BG2(화면블록 0) 맵을 `BAND_MAP` 상수로 떠
두었습니다. 세이브스테이트는 PNG 안의 zlib `gbAs` 청크이고 VRAM 은 오프셋
`0xC00` 부터 `0x18000` 바이트입니다.

### 화면에 나오는 맵 행 순서 (확정)

BG2 의 세로 스크롤은 **HBlank 인터럽트가 줄마다 고칩니다** (HDMA 표가
아닙니다 — 저장 상태의 DMA 채널은 사운드 FIFO 뿐입니다). 그래서 레지스터에
남은 값(`VOFS 8`)은 쓸모가 없고, 화면 y 와 맵 행이 1:1 로 이어지지도 않습니다.

확정 방법은 두 가지를 썼습니다.

1. **타일마다 자기 번호를 바코드로 새긴 실험 롬**을 만들어 찍고 스캔라인마다
   읽었습니다. (주의: 앞 레이어가 각 칸의 5행·5열을 가려서 그 자리는 못 읽습니다.)
2. 패치하지 않은 ROM 의 타이틀 캡처와 각 맵 행을 화소 단위로 대조했습니다.

결과는 이렇습니다 — **18행은 화면에 나오지 않습니다.**

    화면 y  0~ 7 -> 맵 17행       화면 y 32~39 -> 맵 22행
    화면 y  8~15 -> 맵 19행       화면 y 40~47 -> 맵 23행
    화면 y 16~23 -> 맵 20행       화면 y 48~55 -> 맵 24행
    화면 y 24~31 -> 맵 21행       화면 y 56~63 -> 맵 25행

이 순서로 원본을 그리면 캡처와 14,888/15,360 화소가 일치합니다. 처음에는
18~25행이 순서대로 나온다고 보고 19행을 칠하지 않아, 로고 왼쪽 위에 원본
글자 조각이 남았습니다.

핵심은 **원본 글자가 색칠된 글자가 아니라는 점**입니다.

    돌벽 그림에서 글자 모양만 투명(색 0)으로 파내고
    그 가장자리에 흰색(색 15)을 둘렀다

파인 곳으로 뒤 레이어의 물결이 비쳐서 파랗게 보입니다. 이걸 모르고 로고를
그냥 얹으면 배경 투명 부분이 **돌벽에 구멍을 냅니다.** 패치하지 않은 ROM 을
같은 타이밍에 찍어 대조해서 확인했습니다.

그래서 한글화 절차는 세 단계입니다.

1. 일본어 글자가 파인 자리를 8방향 확산으로 주변 돌벽 색으로 메운다
2. 한글 모양을 투명으로 파낸다
3. 그 가장자리에 흰 테두리를 1픽셀 두른다

글자 모양은 아트의 **진한 속**(알파 ≥ 200 이고 밝기 < 150)만 씁니다. 원본
아트의 굵은 흰 테두리는 2,170 -> 190픽셀 축소에서 글자를 다 먹어 버려
못 씁니다. 축소는 면적 평균(`Image.BOX`) 뒤 2×2 열림으로 부스러기를 털고,
테두리는 새로 그립니다.

### 칠할 수 있는 칸이 제한되는 이유 (중요)

타일맵을 만드는 루틴이 **같은 그림의 타일을 하나로 합칩니다.** 그래서 배경이
평평한 칸일수록 다른 자리와 타일을 공유하고, 그 타일을 고치면 **화면 곳곳에
글자 조각이 함께 찍힙니다.** 실제로 처음 빌드에서 맵 0~1행 장식 줄에 글자
부스러기가 나타났습니다.

띠 224칸의 내역은 이렇습니다.

| 종류 | 칸 | 처리 |
| --- | --- | --- |
| 이 띠에서만 쓰는 타일 | 134 | 칠함 |
| 15열/16열 거울 쌍 (`0x0CE`·`0x0EE`) | 4 | 두 칸 그림을 합쳐 칠함 |
| 맵 0~2행 장식 줄과 최대 4번까지 겹침 | 17 | 칠함 (장식 줄 변화가 작음) |
| 장식 줄에서 널리 쓰임 (최대 52곳) | 22 | 못 칠함 |
| 이 블록 밖 타일 (`0x00`–`0x1D`) | 47 | 못 칠함 |

못 칠하는 칸은 대부분 **원본 로고가 비워 둔 자리**입니다(그래서 평평하고,
그래서 합쳐졌습니다). 칠할 수 있는 칸을 그려 보면 이렇습니다.

    행\열  01234567890123456789012345678901
     18    .####...#.....##...#######......
     19    .###############................
     20    .###################.##########.
     21    .################.##.##########.
     22    .##############################.
     23    .##############################.
     24    ..###........######.............
     25    ............########............
           (열 0·31 은 화면 밖)

15열과 16열은 **좌우 반전 거울 쌍**이라 타일 하나를 나눠 씁니다(`0x0CE`는 22행,
`0x0EE`는 23행). 한쪽에 맞춰 그리면 다른 쪽이 뒤집힌 조각으로 나타납니다 —
실제로 「엔」 아래에 사다리꼴 부스러기가 보였습니다. 두 칸이 원하는 그림을
합집합으로(구멍 우선, 다음 흰 테두리) 칠하면 획은 다 살고 글자 사이 여백에
작은 대칭 무늬 하나만 남습니다.

**쓸 수 있는 건 사실상 20~23행 32픽셀**입니다. 원본 비율(4.4:1)대로 키우면
위아래가 잘리므로, `render_wordmark()` 는 가로·세로를 따로 맞춰 **가로로
1.3배쯤 늘인 납작한 로고**를 앉힙니다. 높이 38/36/34 × 폭 224~196 을 훑어
잘리는 잉크가 가장 적은 조합을 고르며, 실측은 **220×36 에서 47/3,863화소
(1.2%)** 입니다. 남은 47화소는 맵 21행 17열·20열(타일 `0x50`·`0x2A`,
장식 줄에서 17·24곳에 쓰임)이라 고칠 수 없습니다.

로고 아래에 남던 사다리꼴 자국은 타일 `0x0B0`(BG2 맵 0행 18열)·`0x10D`
(BG3 맵 31행 11열)·`0x10E`(아예 안 쓰임)였습니다. 후보 타일을 흰색으로
칠한 실험 롬을 찍어 그 자리가 통째로 하얘지는 것으로 확인했고, 투명하게
비우니 뒤의 돌벽이 비쳐 깨끗해집니다 (`OVERLAY_TILES`).

블롭 밖 타일 중 `0x0F`–`0x1D` 는 ROM `0xA65D0` 에 **비압축**으로 있습니다
(`0x00`–`0x0E` 는 물결 애니메이션이라 실행 중 덮어써집니다). 다른 화면에서도
쓰는지 확인하지 못해 건드리지 않았습니다.

팔레트 뱅크 1 은 로고뿐 아니라 화면 테두리 줄무늬 443칸이 함께 쓰므로
**색은 바꾸지 않았습니다.**

부제 `青の天外` 는 타일 `0x160`–`0x165`(48×8) 한 줄뿐입니다. 파란 판 위에
흰 글자라 흰 글자만 지우고 `Galmuri7` 8px 로 `청의 천외` 를 얹습니다.
가까이 있는 `0x120`–`0x12E` 는 `©2003 HUDSON SOFT` 의 중복 제거된 글자
모음이고 `0x140`–`0x147` 은 장식 줄이라, 건드리면 저작권 표기가 깨집니다.

재압축 결과 9,100바이트로 원래 자리 9,577바이트 안에 들어가므로 **제자리에
덮어씁니다.** 포인터를 고칠 필요가 없습니다.

### 오프닝 끝 영문 로고 — `0x6BBDF0` (확정)

오프닝 데모(캐스트 롤)가 끝나고 타이틀로 넘어가기 직전에 영문 「ORIENTAL
BLUE」가 한 번 뜹니다. 그림은 `0x6BBDF0` 의 LZ77 블록 하나(2,276 -> 16,256
바이트)이고, **8bpp 타일 254장**입니다. 바로 뒤(`0x6BC6D4`)가 타이틀
타일셋이라 압축본을 늘릴 수 없습니다.

타일 배치는 **16×16장**이고, 로고를 좌/우 반으로 갈라 세로로 쌓아 두었습니다.

    타일 줄 0~7   -> 그림 왼쪽 절반  (x   0~127)
    타일 줄 8~15  -> 그림 오른쪽 절반 (x 128~255)

이어 붙이면 256×64 그림이 나옵니다. 색은 셋뿐입니다.

| 색 | 뜻 |
| --- | --- |
| 0 | 글자 구멍 (뒤 레이어가 비친다) |
| 1 | 흰 테두리 |
| 2 | 판 (x 0~239) |

타이틀과 같은 **파낸 글자** 방식이지만, 이쪽은 **맵이 순차라 타일을 다른
곳과 나눠 쓰지 않습니다.** 그래서 판을 통째로 색 2 로 밀고 한글을 그대로
앉히면 됩니다. 제약은 압축 크기 하나뿐이라, `build_intro()` 가 높이 53부터
줄이며 2,276바이트에 맞는 가장 큰 크기를 고릅니다 (실측 212×48, 2,272바이트).

### 오프닝 나레이션 — `0x8E4508` / `0x8E6718` (확정)

프롤로그의 `どこまでもつづく　青い空と…` 는 **문자열 표에 없습니다.** 표
805개를 다 펴 봐도 없고, 대응표로 인코딩한 바이트열도 평문에 없습니다.
정체는 **16×16 스프라이트**입니다.

    글리프 그림   ROM 0x8E4508 + attr2*32   (한 글자 = 타일 4장, 1차원 배치)
    스프라이트표  ROM 0x8E6718 부터 8바이트 × 96
    같은 표 사본  ROM 0x8E4208 (글리프는 같고 x 만 다름 — 미끄러지는 애니메이션)
    팔레트 페이드 ROM 0x8E3D00 (16색 × 여러 단계)

한 칸은 OAM 과 같은 모양입니다 — `attr0`(y·크기) `attr1`(x·반전·크기)
`attr2`(글리프), 뒤에 2바이트 여백. VRAM 에 올릴 때 타일 0x30 이 더해집니다.

구조는 이렇게 풀었습니다.

1. `tools/konarr.py --probe` 로 **글리프 칸마다 번호를 새긴 롬**을 만들어
   실기에서 찍었습니다. 화면에 뜬 숫자가 곧 그 자리의 글리프 번호입니다.
2. 거기서 얻은 글리프↔글자 대응으로 표 96칸을 전부 해독했습니다.

    한 줄     = 레코드 묶음 (`konarr.LINES`)
    글자 순서 = **x 내림차순** (표에는 오른쪽 글자가 먼저 들어 있습니다)

y 값은 줄을 그대로 나누지 않습니다. 한 y 묶음에 두 줄이 x 범위를 겹쳐 가며
섞여 있어서, 레코드 번호로 나눠야 합니다.

| 줄 | 원문 | 레코드 | 칸 |
| --- | --- | --- | --- |
| L1 | どこまでもつづく　青い空と | 25–36 | 12 |
| L2 | どこまでもつづく　青い海をうつし | 10–24 | 15 |
| L3 | ここに　青の大地がある | 0–9 | 10 |
| L4 | この地に　すむものは | 47, 67–74 | 9 |
| L5 | たとえ　それが小さな命であろうと | 51–65 | 15 |
| L6 | ＜青＞のいみを　しるものである | 37–46, 48–50, 66 | 14 |
| L7 | ここは　青の大地 | 85, 89, 90, 92–95 | 7 |
| L8 | すべての命が　いきる大地 | 78–84, 86–88, 91 | 11 |
| — | 「・・・」 | 75–77 | 3 |

한글화는 **`attr2` 만 바꿉니다.** x 는 건드리지 않습니다 — 두 표가 같은 글을
서로 반대 방향으로 담고 있어서(한쪽은 x 내림차순, 다른 쪽은 오름차순) 한쪽
기준으로 다시 배치하면 다른 쪽이 뒤집힙니다. 실제로 그렇게 해 보고 화면에서
글이 거꾸로 나오는 것을 확인했습니다.

원문은 줄마다 **한 곳만** 띄어 있습니다(칸 사이가 두 배로 벌어진 자리).
번역문도 그 자리에서 끊어야 틈이 엉뚱한 데 생기지 않습니다 —
L1·L2 는 8자 뒤, L3·L5·L7 은 3자 뒤, L4 는 4자 뒤, L6 은 7자 뒤, L8 은 6자 뒤.

글자는 획 3 · 둘레 1 로 그립니다. 원본은 바깥에 2 를 한 겹 더 두르지만
한글은 획이 촘촘해서 한 겹만 둘러야 읽힙니다. 폰트는 Galmuri14 를 **14픽셀**
그대로 써야 하고(12픽셀로 줄이면 자모가 깨집니다), 글리프 칸은 48개를
씁니다(「・・・」 글리프 앞까지 52개가 한도).
