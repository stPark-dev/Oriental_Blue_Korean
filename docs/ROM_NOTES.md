## 확인된 구조

### 문자 선택 그리드 — `0x08ADEC`, `0x08B142`

이름 입력 화면에서 쓰는 문자표입니다. **셀당 2바이트 고정폭**, 행당 16셀입니다.

- 반각 문자: `20 XX` — 상위 바이트가 `0x20`, 하위 바이트가 ASCII 코드
- 전각 문자: Shift-JIS 2바이트를 그대로 저장
- 빈칸: `20 20`

| 오프셋 | 셀 수 | 내용 |
| --- | --- | --- |
| `0x08ADEC` | 384 | 반각 ASCII 전체 → 전각 숫자 → 전각 영대문자 → 히라가나 |
| `0x08B142` | 597 | 가타카나(탁음·반탁음·요음 포함) → 상용 한자 약 215자 |

중복을 제거하면 **522자**입니다. 추출:

```bash
make grid          # build/grid_*.tbl 생성 (ROM 파생물이라 커밋하지 않습니다)
make grid-find     # 다른 그리드 후보 탐색
```

시사점: 게임이 **Shift-JIS를 그대로 다루는 경로가 존재**합니다. 다만 이 표는
이름 입력용이며, 본편 스크립트가 같은 인코딩을 쓴다는 근거는 아직 없습니다.

### 압축 데이터 — GBA 표준 LZ77

ROM 전역에서 GBA BIOS 표준 LZ77(`0x10`) 블록이 쓰입니다.

포인터 유도 스캔(`--via-pointers`) 결과:

| 항목 | 값 |
| --- | --- |
| 검사한 포인터 대상 | 34,110곳 |
| 유효 압축 블록 | **353개** |
| 압축 해제 후 총량 | **13,057,829바이트** |
| 평균 압축률 | 약 45–60% |

ROM 16MB 중 13MB가 압축 데이터이므로, 대부분이 그래픽·사운드로 보입니다.

> 전수 스캔(4바이트 정렬 400만 곳)은 수십 분이 걸립니다. 압축 블록은 거의 항상
> 포인터로 참조되므로 `--via-pointers` 를 쓰면 수 분으로 줄어듭니다.

```bash
make scan-lz       # 또는: python3 tools/gbalz.py scan ROM --via-pointers
```

## 미확인 / 진행 중

### 본편 스크립트 — 위치·압축·인코딩 확인 완료

정적 디스어셈블(`tools/disasm.py`)로 호출 경로를 역추적해 전부 밝혀냈습니다.

#### 호출 경로

```
VM 핸들러 0x08039CCC(ctx, ?, id, kind)
  └ kind != 2 면 즉시 0 반환
  └ 0x08038930(id)
      └ table = *(u32*)(0x02002C00 + 0xAC)     ; EWRAM 전역에 담긴 테이블 포인터
      └ 0x0800D574(table, id)                  ; 테이블 조회
          └ 0x0800D558(addr)                   ; 4KB 작업 버퍼로 전개
              └ 0x0800D4F8(addr, 0x1000)       ; 압축 해제 본체
          └ 반환 0x02002E60 (EWRAM 작업 버퍼)
  └ 0x0801B8C8(ctx, 버퍼)                      ; 출력
```

#### 문자열 테이블 형식 (`0x0800D574`)

```
table[0]          엔트리 개수
table[id]         테이블 기준 상대 오프셋
주소 = table + table[id]
유효 범위는 0 < id < count. 벗어나면 빈 문자열 0x08089D44 를 반환합니다.
```

#### 압축 형식 (`0x0800D4F8`)

출력 바이트 수를 예산으로 삼는 LZ 계열입니다. **역참조가 압축 스트림 자체를
가리키며 재귀적으로 전개**되는 점이 특징입니다.

| 바이트 | 의미 |
| --- | --- |
| `0x08` | 이스케이프. 뒤 2바이트 `b1 b2` — 길이 `(b1>>4)+4`, 거리 `((b1&0x0F)<<8)\|b2` |
| `0x00` | 종결자 |
| 그 외 | 문자 코드 그대로 |

#### 문자 인코딩

전개된 텍스트는 `<코드> <파라미터>` 형태가 주를 이룹니다. 디코더 `0x0803894C`
가 코드 `1`–`5` 에 대해 뒤따르는 1바이트를 함께 읽습니다.

| 코드 | 출현 횟수 | 해석 |
| --- | --- | --- |
| 직접(≥6) | 284,624 | 1바이트 문자 |
| `01` | 80,210 | 2바이트 문자 (뱅크 1) |
| `02` | 16,883 | 2바이트 문자 (뱅크 2) |
| `04` | 429 | 미상 |
| `05` | 292 | 미상 |
| `03` | 250 | 미상 |

> **가설**: `01`/`02` 는 문자 뱅크 선택자이고 뒤 1바이트가 뱅크 내 인덱스입니다.
> 뱅크 수 × 256 이면 일본어 RPG에 필요한 자수를 감당할 수 있습니다.
> `03`–`05` 는 출현이 적어 서식 제어(이름 삽입, 대기, 색상 등)로 추정됩니다.

#### 규모

| 항목 | 값 |
| --- | --- |
| 문자열 테이블 | 133개 |
| 엔트리 | 22,305개 |
| 압축 해제 성공 | 22,143개 (**99.27%**) |
| 실패 | 162개 (0.73%, 원인 미확인) |
| 전개 후 총량 | 501,330바이트 |

테이블은 대부분 `0xDD0000`–`0xDFFFFF` 에 몰려 있으며, 이는 일/영 대조에서
가장 크게 바뀐 구간(`0xDB0C08` 이후)과 일치합니다.

엔트리가 많은 테이블: `0xDE865C`(2,361) `0xDDE1E4`(1,923) `0xDF9088`(1,591)
`0xDFBEE4`(1,411) `0x26CAC8`(1,384) `0xDE1AF8`(1,018)

```bash
python3 tools/obtext.py scan   rom/baserom.gba --min-count 32
python3 tools/obtext.py table  rom/baserom.gba 0xDE865C --limit 10
python3 tools/obtext.py expand rom/baserom.gba 0xDEAB40
```

### 영문 패치 ROM 대조

이 게임은 해외 정식 발매가 없었으므로, 흔히 "북미판"으로 도는 파일은
**영문 팬 번역 패치가 적용된 ROM**입니다.

| 항목 | 일본판 | 영문 패치판 |
| --- | --- | --- |
| 크기 | 16,777,216 | 16,777,216 (동일) |
| 내부 타이틀 / 코드 | `ORIENTALBLUE` / `AORJ` | 동일 |
| CRC32 | `05E80ECC` | `8A850DA7` |
| SHA-1 | `414cad1a…` | `95c4e8b7…` |

대조 결과:

| 측정 | 값 | 해석 |
| --- | --- | --- |
| 전체 상이 바이트 | 11,281,332 (67.24%) | 데이터 영역을 대폭 재구성 |
| **앞 1MB(코드 영역) 상이** | **2,961바이트 (0.28%)** | 엔진 훅은 소규모 |
| 128B 이상 동일 구간 | 392개 / 4,389,063B | 최장 `0x26E06B`(1.8MB), `0x0BD23A`(1.0MB) |
| 영문판 평문 ASCII 비율 | 1.24% | **영문판도 평문으로 저장하지 않음** |

가장 중요한 결과는 마지막 줄입니다. 영문 패치판조차 텍스트가 평문 ASCII로
보이지 않으므로, **게임 고유의 인코딩/압축 체계를 그대로 유지한 채 번역**한
것입니다. 즉 우리도 같은 체계를 해독해야 합니다.

### 이벤트 VM 레코드 — `0x092000`–`0x0A4000` (구조 확정)

영문 패치가 집중적으로 수정한 구간입니다. **20바이트 고정 레코드**가
연속으로 늘어서 있습니다 (레코드 2,234개, 핸들러 438종).

```
+0   u16  field0     인덱스/순번으로 추정
+2   u16  width      메시지 창 줄당 글자 수
+4   u16  lines      메시지 창 줄 수
+6   u32  handler    THUMB 함수 포인터 (최하위 비트 = 1)
+10  u16  field10    순번 (0,1,2,… 로 증가하는 사례 다수)
+12  u16  field12
+14  u16  field14
+16  u16  field16
+18  u16  field18
```

레코드 크기는 포인터 간 간격 분포에서 확정했습니다 — 20바이트가 2,194회로 압도적.

#### width / lines 의 의미 (확인됨)

핸들러 `0x0803B604` 의 레코드 16개는 **전부 일관**됩니다.

| 필드 | 일본판 | 영문 패치판 |
| --- | --- | --- |
| `width` | 8 (16/16개) | 16 (16/16개) |
| `lines` | 2 (16/16개) | 1 (16/16개) |
| `field12` `field14` `field16` | 동일 | 동일 |

같은 `8×2 → 16×1` 변화가 `0x08045304`, `0x08046EC8`, `0x080472A4`,
`0x08046F00`, `0x08047018` 에서도 각각 16회씩 나타납니다.

**일본어 전각 8자 × 2줄 = 영어 반각 16자 × 1줄** — 전각 1칸이 반각 2칸이므로
픽셀 폭이 보존됩니다. 즉 이 필드의 단위는 픽셀이 아니라 **문자 칸**입니다.

> **한글화 시사점**: 한글을 전각 폭(일본어와 동일)으로 렌더링하면 일본판 값
> `8×2` 를 **그대로 두면 됩니다**. 반각에 가까운 좁은 한글 폰트를 쓸 경우에만
> 이 필드를 다시 계산해야 합니다. 폰트 폭 결정이 이 값에 직결됩니다.

```bash
python3 tools/vmrec.py rom/baserom.gba --stats --min-count 8
python3 tools/vmrec.py rom/baserom.gba --fn 0x0803B604 --diff 영문판.gba
```

#### 주의 — 필드 의미는 핸들러마다 다릅니다

처음에는 레코드 2,234개를 한꺼번에 통계 냈고, 그 결과 `(2,8) → (1,16)` 처럼
필드 순서가 뒤바뀐 듯한 사례와 곱이 보존되지 않는 273건이 섞여 나왔습니다.
**핸들러 438종을 구분하지 않은 탓**이었습니다. 같은 20바이트 틀을 쓰더라도
인자의 의미는 핸들러마다 다르므로, 반드시 `--fn` 으로 나눠서 봐야 합니다.

#### 자주 호출되는 핸들러

| 주소 | 참조 횟수 |
| --- | --- |
| `0x08039CCC` | 270 |
| `0x08039CF4` | 179 |
| `0x0804A9FC` | 96 |
| `0x0803A58C` / `0x0803A5D8` | 각 26 |

이들이 텍스트 출력 루틴의 진입점 후보이며, 동적 분석 시 브레이크포인트
1순위입니다.

### 문자 대응표 — 확정

문자표는 이름 입력 그리드와 **같은 배열**입니다. `0x08ADEC` 부터 셀당 2바이트가
연속으로 이어지며, **문자 코드가 곧 셀 인덱스**입니다.

```
코드 = (뱅크 << 8) | 인덱스

  0x000–0x0FF   본문에 1바이트로 그대로 등장
  0x100–0x1FF   `01 XX` 2바이트로 등장
  0x200–0x2FF   `02 XX` 2바이트로 등장
```

#### 확정 근거

1. **빈도 일치** — 직접 코드의 최빈값들이 일본어 히라가나 빈도와 정확히 맞습니다.
   `0xC3`=の(13,645회), `0xAC`=い, `0xB0`=か, `0xAD`=う, `0xB6`=し, `0xBA`=た,
   `0xD8`=ん, `0xBF`=な, `0xBE`=と, `0xC4`=は … 상위 14개가 전부 고빈도 히라가나입니다.
2. **셀 인덱스 일치** — `'あ'` 는 그리드 셀 171번이고 코드도 `0xAB`(=171)입니다.
   최빈 코드 `0x90`(26,886회)은 셀 144번 전각 공백으로, 최다 출현이 자연스럽습니다.
   ASCII 구간도 `코드 == ASCII 값` 으로 그대로 맞아떨어집니다.
3. **실문자열 검증** — 이 대응표로 디코딩하면 몬스터·인물 이름이 정상적인
   일본어로 읽힙니다. 뱅크 기준점을 `0x180`/`0x280` 으로 바꾸면 의미 없는
   한자 나열이 되어, 기준점이 `0x100`/`0x200` 임이 확정됩니다.

#### 대응 범위

| 구분 | 자수 |
| --- | --- |
| 직접 (1바이트) | 211자 |
| 뱅크 `01` | 151자 |
| 뱅크 `02` | 198자 |

### 기각된 가설

같은 길로 다시 들어가지 않도록, 확인해서 아니었던 것들을 남깁니다.

| 가설 | 검증 방법 | 결과 |
| --- | --- | --- |
| 스크립트가 비압축 평문 Shift-JIS | 전 ROM SJIS 연속 구간 스캔 | **기각**. ROM의 0.82%만 SJIS로 읽히고, 최장 구간(`0x6E6C81`)은 `C9 99` 반복의 그래픽 데이터 |
| 압축 블록 안에 평문 Shift-JIS | 353개 블록 압축 해제 후 SJIS 비율 측정 | **기각**. 전부 0.5–6.3% (텍스트라면 90%↑) |
| 2바이트 LE 문자 인덱스 | 후보 블록(`0x0B4BF0`)을 16비트 값으로 해석 | **기각**. 최빈값이 `0xC0C0`·`0x2A2A`·`0x7575` 등 동일 바이트 쌍 → 4bpp 타일 그래픽 |
| `0x0B154C` 706개 테이블이 메시지 테이블 | 대상 오프셋 분포 확인 | **보류**. 대상 중 171/706만 압축 헤더, 비정렬. 혼합 데이터로 보임 |
| 1바이트 커스텀 인코딩의 제한 알파벳 구간 | 256바이트 창 단위 고유 바이트 수 스캔 | **결정적이지 않음**. 검출된 구간의 최빈 바이트가 `F0`·`01` 편중 → 압축 스트림 또는 사운드 데이터로 추정 |

### 다음 수단: 동적 분석

정적 스캔으로는 한계에 도달했습니다. 가장 확실한 방법은 **에뮬레이터 디버거로
글자 출력 루틴을 잡는 것**입니다.

1. mGBA 또는 no$gba 디버거로 게임 실행, 대사창이 뜨는 지점까지 진행
2. 폰트 타일이 올라가는 VRAM 주소(`0x06000000`대)에 쓰기 브레이크포인트
3. 멈춘 지점에서 역추적 — 글리프를 읽어오는 소스 주소가 **폰트 데이터 위치**
4. 그 루틴에 넘어오는 인자가 **문자 코드** → 인코딩 체계가 드러남
5. 문자 코드를 읽어오는 버퍼를 따라가면 **스크립트 블록 위치**

리눅스에서는 mGBA가 GDB 스텁을 제공하므로 `mgba -g` 로 띄운 뒤
`gdb-multiarch` 로 붙으면 스크립트 가능한 디버깅이 됩니다.
